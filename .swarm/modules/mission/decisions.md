## 2026-08-21 — Missions must verify their own work through the harness, because the sandboxed work agent cannot. Evidence from a real product repo (new-self): every module of every mission ended partial, with pytest, npm, node, xcodebuild and even git refused by the permission layer (permission-mode acceptEdits, headless, no approver present), agents burned 3-9M tokens retrying blocked commands and hand-tracing tests instead of running them, and a real regression shipped (a call passing a field its target dataclass does not have) because nothing ever executed. Three coordinated, generic changes. (1) After a module work agent finishes and BEFORE review, if config.verifyCommand is set, the harness must run it in that module's worktree — reuse or extract the runVerify helper that already exists in packages/core/src/loop/run.ts around line 412 into a shared location; on failure, re-spawn the same agent via the runtime's existing resume support (spec.resume in claude-code-local.ts) with the trimmed verify output and the instruction to fix and report again; loop up to a new config field maxVerifyRounds (default 2); record the final verify outcome (passed, failed, or skipped-no-command) on the module result, in the mission report, and in the CLI output. (2) Tell the work agent the truth about its environment: the work prompt currently ends with the line 'Do the work, verify it, then report.' (mission/run.ts around line 412) — an instruction the sandboxed agent cannot obey and the direct cause of the blocked-command retry loops; change that prompt contract to state it must NOT attempt to run tests, builds, package managers or git (they will be refused and waste its context), that the harness runs the project's verify command after it reports and hands back failures to fix, and that its edits are the deliverable. (3) Make refused permissions visible: detect and count 'requires approval' tool refusals in the translated agent event stream, expose the count on the module result and in the mission report, so a misconfigured project is diagnosable at a glance instead of buried in prose. Keep the changes runtime-agnostic: resume and the event stream are the adapter's seams; the verify loop lives in the mission layer. Cover the verify loop (pass, fail-then-fix, fail-after-max-rounds, no-command) and the refusal counter with tests.

- Follow-up: swarm-orchestration: migrate loop/run.ts to import runVerify from '../mission/verify.js' and delete its own inline copy (this was explicitly their side of the same contract).
- Follow-up: workspace-git: add `maxVerifyRounds: number` (default 2) to SwarmConfig/config.ts — once landed, remove the `as SwarmConfig & {maxVerifyRounds?: number}` cast in mission/run.ts.
- Follow-up: runtime: expose `refusalCount` on AgentOutcome (via claude-code-local.ts's translated event stream) — once landed, remove the `as AgentOutcome & {refusalCount?: number}` cast in mission/verify-loop.ts.

## 2026-08-21 — The branch commit must respect the module boundary — ownership is currently computed but not enforced where it matters. Evidence from a real product repo (new-self): one module's diff silently deleted four real audio assets and their credits manifest belonging to another module, machine-specific junk (a .venv symlink) landed in a branch, and ownership violations kept appearing mission after mission; checkOwnership (mission/run.ts) reports them, but commitAll (packages/core/src/git/worktree.ts) still stages everything with git add -A, so the boundary is information, not mechanism. Change the mission commit step so it produces at most two commits on the module branch: (1) the main commit containing only changes to paths inside the module's owns globs, and (2) a separate quarantine commit containing every change outside them — additions, modifications AND deletions — with a message prefixed 'OUT OF BOUNDS (<module-slug>):' followed by the offending paths, so a human can drop it with a single rebase gesture while the main commit stays clean. When nothing is out of bounds there is no second commit; when EVERYTHING is out of bounds the main commit is skipped and only the quarantine commit exists. Keep the existing linked-path exclusion exactly as is (linked paths are never committed at all, in either commit). Deletions outside the boundary are the dangerous case that motivated this — make sure a staged deletion of a non-owned file ends up only in the quarantine commit, never in the main one. Surface the split in the module result, the mission report and the CLI output: which paths were quarantined and the quarantine commit's short hash, next to the existing ownership-violation list. Implementation note: the ownership matcher already exists (isOwned / checkOwnership in the swarm-orchestration module's ownership.ts, exported via the core barrel); the commit helper lives in the workspace-git module's worktree.ts — a two-phase git add with pathspecs (add the owned set, commit, add the rest, commit) is the expected shape, and git pathspec exclude magic ':(exclude)' plus explicit path lists are both acceptable as long as globs with special characters are handled. Add tests covering: owned-only change producing one commit; mixed change producing two commits with the correct file split; an out-of-bounds deletion landing only in the quarantine commit; everything-out-of-bounds producing only the quarantine commit; and linked paths staying uncommitted in both.

- Follow-up: This module's part of the task (wiring commitAll's new contract into run.ts) cannot be completed until the workspace-git module ships the new commitAll(worktreePath, moduleSlug, ownsGlobs, message, linked) => {mainCommitHash?, quarantineCommitHash?, quarantinedPaths} contract in packages/core/src/git/worktree.ts. Once it does, re-apply: pass spec.slug and spec.owns into the call, remove the placeholder consts, and read quarantinedPaths/quarantineCommitHash/mainCommitHash off the real return value (confirming whether it still returns ok/detail or throws on failure, since that determines whether the call needs a try/catch).
