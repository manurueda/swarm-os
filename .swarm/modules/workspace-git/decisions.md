# Workspace & Git Worktrees — decisions

Append-only log. One entry per consequential choice, newest at the bottom.

## 2026-08-15 — Swarm OS links dependency directories into every agent worktree so agents can build, and then commits them. linkDependencies creates a symlink named node_modules; the conventional ignore rule in a JavaScript project is 'node_modules/' with a trailing slash, which matches a directory and not a symlink. So commitAll's 'git add -A' stages it, every mission branch ends up carrying an absolute path to one developer's machine, and changedFiles reports it as an ownership violation on every mission. The linked names are already available on WorktreeHandle.linked. Make the linked paths invisible to both commitAll and changedFiles, without depending on the target repository's own .gitignore and without modifying any file the developer owns. Add tests that create a real temporary git repository and prove a linked path is neither committed nor reported as changed. npm test must pass.

- Follow-up: mission/run.ts (a different module, outside my globs) still calls changedFiles(worktreePath, base) and commitAll(worktreePath, message) without the new third argument, and discards handle.linked (it goes out of scope after the worktree-creation try block). It needs a small change — capture `handle.linked` in an outer-scoped variable and pass it as the third argument to both calls — to actually close this bug end-to-end in production; without that change this module's fix only benefits direct callers of the git wrapper, not the real mission-run path.
- Follow-up: npm test / npm run build could not be executed in this session due to sandbox/permission restrictions blocking all code-execution commands; needs to be run in an environment where that's possible before merging.

## 2026-08-21 — The branch commit must respect the module boundary — ownership is currently computed but not enforced where it matters. Evidence from a real product repo (new-self): one module's diff silently deleted four real audio assets and their credits manifest belonging to another module, machine-specific junk (a .venv symlink) landed in a branch, and ownership violations kept appearing mission after mission; checkOwnership (mission/run.ts) reports them, but commitAll (packages/core/src/git/worktree.ts) still stages everything with git add -A, so the boundary is information, not mechanism. Change the mission commit step so it produces at most two commits on the module branch: (1) the main commit containing only changes to paths inside the module's owns globs, and (2) a separate quarantine commit containing every change outside them — additions, modifications AND deletions — with a message prefixed 'OUT OF BOUNDS (<module-slug>):' followed by the offending paths, so a human can drop it with a single rebase gesture while the main commit stays clean. When nothing is out of bounds there is no second commit; when EVERYTHING is out of bounds the main commit is skipped and only the quarantine commit exists. Keep the existing linked-path exclusion exactly as is (linked paths are never committed at all, in either commit). Deletions outside the boundary are the dangerous case that motivated this — make sure a staged deletion of a non-owned file ends up only in the quarantine commit, never in the main one. Surface the split in the module result, the mission report and the CLI output: which paths were quarantined and the quarantine commit's short hash, next to the existing ownership-violation list. Implementation note: the ownership matcher already exists (isOwned / checkOwnership in the swarm-orchestration module's ownership.ts, exported via the core barrel); the commit helper lives in the workspace-git module's worktree.ts — a two-phase git add with pathspecs (add the owned set, commit, add the rest, commit) is the expected shape, and git pathspec exclude magic ':(exclude)' plus explicit path lists are both acceptable as long as globs with special characters are handled. Add tests covering: owned-only change producing one commit; mixed change producing two commits with the correct file split; an out-of-bounds deletion landing only in the quarantine commit; everything-out-of-bounds producing only the quarantine commit; and linked paths staying uncommitted in both.

- Follow-up: mission module: in packages/core/src/mission/run.ts around line 517, change `commitAll(worktreePath, message, linked)` to `commitAll(worktreePath, spec.slug, spec.owns, message, linked)`, replace `committed = commit.ok` / `if (!commit.ok) commitError = commit.detail` with logic based on `commit.mainCommitHash`/`commit.quarantineCommitHash` (e.g. `committed = commit.mainCommitHash !== undefined || commit.quarantineCommitHash !== undefined`), and surface `commit.quarantinedPaths`/`commit.quarantineCommitHash` on the returned MissionModuleResult next to `ownershipViolations`.
- Follow-up: runtime module: add optional quarantinedPaths?: string[] and quarantineCommitHash?: string fields to the relevant persisted type in packages/core/src/types.ts, and re-export the CommitSplit type from packages/core/src/index.ts alongside the existing commitAll export.
- Follow-up: cli module (or wherever mission results are printed): surface quarantinedPaths/quarantineCommitHash in CLI output next to the existing ownership-violation list, per the mission's reporting requirement.
