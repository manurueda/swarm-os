## 2026-08-21 — Add a stale-build warning to the swarm CLI. When running from a git install (detectInstall kind git), print a single warning line at command start — wired at the same point as noticeIfUpdated — whenever the TypeScript sources look newer than the compiled build, telling the user to run npm run build. Rationale: the auto-updater only covers being behind origin; a developer who commits locally and forgets to rebuild silently runs old code. Implementation constraints: mtime checks only, mirroring the fast path tsc --build itself uses — for each of packages/core and packages/cli, compare the newest source input mtime against that package's tsconfig.tsbuildinfo mtime. Do NOT compare source mtimes against dist output mtimes: tsc --build refreshes tsbuildinfo but skips emitting dist when touched files hash unchanged, so dist comparisons false-positive. A missing tsbuildinfo counts as stale. The check must never slow a command perceptibly, must swallow every error (a failed check must never break or fail a command), and must not run inside the background update worker (SWARM_UPDATE_WORKER env set). Cover the comparison logic with tests, and mention the behavior in the CLI help text next to the existing updates line.

- Follow-up: Once the `runtime` module's `checkStaleBuild` export lands in packages/core, run `npm run build` at the repo root and manually verify: `swarm --help` shows the new line near the updates paragraph; a git install with a touched source file and missing/stale tsconfig.tsbuildinfo prints exactly one warning at command start; no warning prints when SWARM_UPDATE_WORKER is set or install kind isn't git; a thrown error from checkStaleBuild never surfaces.

## 2026-08-21 — Missions must verify their own work through the harness, because the sandboxed work agent cannot. Evidence from a real product repo (new-self): every module of every mission ended partial, with pytest, npm, node, xcodebuild and even git refused by the permission layer (permission-mode acceptEdits, headless, no approver present), agents burned 3-9M tokens retrying blocked commands and hand-tracing tests instead of running them, and a real regression shipped (a call passing a field its target dataclass does not have) because nothing ever executed. Three coordinated, generic changes. (1) After a module work agent finishes and BEFORE review, if config.verifyCommand is set, the harness must run it in that module's worktree — reuse or extract the runVerify helper that already exists in packages/core/src/loop/run.ts around line 412 into a shared location; on failure, re-spawn the same agent via the runtime's existing resume support (spec.resume in claude-code-local.ts) with the trimmed verify output and the instruction to fix and report again; loop up to a new config field maxVerifyRounds (default 2); record the final verify outcome (passed, failed, or skipped-no-command) on the module result, in the mission report, and in the CLI output. (2) Tell the work agent the truth about its environment: the work prompt currently ends with the line 'Do the work, verify it, then report.' (mission/run.ts around line 412) — an instruction the sandboxed agent cannot obey and the direct cause of the blocked-command retry loops; change that prompt contract to state it must NOT attempt to run tests, builds, package managers or git (they will be refused and waste its context), that the harness runs the project's verify command after it reports and hands back failures to fix, and that its edits are the deliverable. (3) Make refused permissions visible: detect and count 'requires approval' tool refusals in the translated agent event stream, expose the count on the module result and in the mission report, so a misconfigured project is diagnosable at a glance instead of buried in prose. Keep the changes runtime-agnostic: resume and the event stream are the adapter's seams; the verify loop lives in the mission layer. Cover the verify loop (pass, fail-then-fix, fail-after-max-rounds, no-command) and the refusal counter with tests.

- Follow-up: Once the mission module's MissionModuleResult change is merged, consider replacing the `as unknown as {...}` casts in mission.ts's verifyOutcomeOf/refusalCountOf with direct property access — the defensive cast can be dropped as a small follow-up cleanup once the real type is confirmed to match.
- Follow-up: If historical visibility into verifyOutcome/refusalCount for past missions (`swarm missions`) is wanted, the runtime module would need to add these fields to AgentLedgerEntry/MissionRecord and mission.ts would need to persist them there — out of scope for cli alone since types.ts is owned by runtime.

## 2026-08-21 — Remediate the reviewer findings from the commit-boundary mission, now integrated into main. Surgical fixes only. In the workspace-git module, packages/core/src/git/worktree.ts: (1) MAJOR — commitStaged commits the entire index, so anything a work agent had already staged by hand before commitAll runs (the historical case: git add of a linked .venv symlink) still slips into the main commit; the old commitAll neutralized this by unconditionally running git rm --cached on hidden/linked paths before committing. Restore that protection under the new two-phase shape: before classifying paths, reset the index to HEAD (git reset -q) so commitAll fully owns what gets staged, and keep the existing hidden/linked filtering as is; add a test where a linked path and an out-of-bounds file are pre-staged by hand before commitAll and prove the linked path lands in neither commit and the out-of-bounds file lands only in quarantine. (2) MINOR — statusPaths parses git status --porcelain, which collapses an entirely new untracked directory into a single 'dir/' line, so ownership classification runs against the directory instead of the files inside it and can misfile them; use status --porcelain -uall so every file is listed individually, and add a test with a new untracked directory containing one owned and one out-of-bounds file. In the mission module, packages/core/src/mission/run.ts: (3) add the missing test coverage the reviewer flagged for the quarantine plumbing — the renderMissionReport 'Quarantined' branch and the field flow from a CommitSplit into MissionModuleResult (a unit test at whatever seam run.ts exposes; do not spawn real agents). In the cli module, packages/cli/src/commands/mission.ts: (4) quarantinedPathsOf/quarantineCommitHashOf read fields through 'as unknown as' casts even though MissionModuleResult now declares them — drop the casts and use the typed fields directly; and add the small rendering test the reviewer noted for the quarantine display block (truncation and hash formatting), in the loosened substring style the file's other tests now use.
