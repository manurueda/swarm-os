## 2026-08-15 — detectDrift in packages/core/src/mapper/pipeline.ts reports drifted: true whenever the repository digest hash differs from the recorded one, but changedModules only lists modules whose OWN files moved. Those two can disagree: the digest covers every tracked file, including files no module owns. Since .swarm/ became tracked, the map itself rewrites tracked files on every run, so immediately after a successful full map 'swarm status' prints the warning '0 module(s) changed since mapping' with an empty list - a warning that fires on a perfectly healthy repository. A signal that fires when nothing is wrong teaches people to ignore the signal, which is the one thing this project's own architecture notes say must not happen. Make drifted mean what its consumers use it for: there is module work to do. If no module's files changed there is nothing to re-analyse, whatever the whole-repo digest says. Keep reporting genuinely unanalysed modules as drift, since those need work regardless. Add tests covering both: a repo whose digest moved but no module did is not drifted, and a module with no recorded hash still is. npm test must pass.

## 2026-08-21 — Swarm OS must not run blind without a verify command — detect one instead of defaulting to nothing. Evidence from a real product repo (new-self): swarm map generated .swarm/config.yaml with verifyCommand empty, nothing ever warned, and seven missions ran with zero executable verification; now that the harness runs verifyCommand in each module worktree and loops the agent on failures, an empty verifyCommand silently disables that entire mechanism, so leaving it blank must become a visible, deliberate choice. Two changes. (1) Detection at map time: when swarm map creates the project config, or updates a config whose verifyCommand is empty, detect a candidate by pure file inspection — never execute anything: a package.json at the repo root with a scripts.test entry that is not the npm placeholder (exact string containing 'no test specified') suggests npm test, and if only a scripts.build exists suggest npm run build; a pyproject.toml, pytest.ini, setup.cfg with a [tool:pytest] section, or a tests/ directory containing .py files suggests pytest -q, preferring .venv/bin/python -m pytest -q when a .venv directory exists at the repo root; a Cargo.toml suggests cargo test; a go.mod suggests go test ./...; a Makefile with a test: target suggests make test. When several apply, prefer the one matching the repo's dominant language from the digest the mapper already computes, and record the others in the map output as alternatives. Persist the chosen command into config verifyCommand only when it was empty — never overwrite a non-empty value the user set — and say clearly in the map output what was chosen and why, or that nothing was detected and missions will run without verification until verifyCommand is set. (2) A doctor check: swarm doctor, when run inside a repo that has a .swarm config, must add a check that fails soft (warn, not fail) when verifyCommand is empty, explaining that the mission verify loop is disabled without it and printing the detected suggestion from the same pure detection helper, or how to set it. Put the detection helper where both the mapper and the doctor command can reach it without a dependency cycle, add tests for the full detection matrix including the several-candidates and the nothing-detected cases, and keep every check pure filesystem inspection.

- Follow-up: cli's doctor command needs a new soft-fail check for empty verifyCommand, calling detectVerifyCommand(repoRoot, dominantLanguage) directly and printing its suggestion or 'how to set it' — out of this module's boundary (packages/cli/**).
